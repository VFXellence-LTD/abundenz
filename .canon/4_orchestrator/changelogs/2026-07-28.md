# Changelog — 2026-07-28

## Session ~01:00–01:20 — Mission Control boot crash fix (stale v_forge_* views)

**Issue:** [#22](https://github.com/VFXellence-LTD/abundenz/issues/22) (VFXellence-LTD/vfxellence, renamed to abundenz)

### Symptom

Server boot crashed on production DB: `SqliteError: error in view v_forge_agent_runs: no such column: ecosystem_id` at `migrateSetupBrandScope` (`db.ts:262`). Port 4500 never bound → Vite proxy 502 on all API routes (`/campaigns`) → brand creation showed generic "Could not create the brand. Try again."

### Root cause chain

1. `agent_runs` schema (`db.ts:98`) lost `ecosystem_id` (became campaign-linked), but `scoping.ts` `SCOPED_TABLES` still included `agent_runs` → generated `v_*_agent_runs` views selecting a missing column. SQLite validates views lazily, so creation succeeded — time bomb.
2. Orphan `v_forge_*` views (old "apps"/forge codename era) were never in the static `LEGACY_VIEWS` drop list.
3. SQLite re-validates ALL views on ANY `ALTER TABLE` → `migrateSetupBrandScope`'s `ALTER TABLE ... RENAME` threw on the first broken view → boot crash.
4. Additive ALTER loop in `db.ts` used blanket `catch {}` — silently masked the corruption for weeks.
5. Side finding: an old tsx-watch process carried stale `DB_PATH=e2e-test.db` in its shell env — days of writes went to `e2e-test.db` (split-brain vs default `mission-control.db`).

### Files changed

- `.mission-control/server/scoping.ts` — removed `agent_runs` from `SCOPED_TABLES`; static `LEGACY_VIEWS` replaced with dynamic `dropScopedViews()` enumerating `sqlite_master` for `v_%` views; `createScopedViews` now drop+recreate.
- `.mission-control/server/db.ts` — `dropScopedViews()` called BEFORE additive ALTERs and `migrateSetupBrandScope`; additive catch rethrows unless "duplicate column name".
- `.mission-control/server/test/setup.migration.test.ts` — regression test reproducing production state (orphan broken views + pre-`brand_id` setup tables).
- `.mission-control/client/src/components/BrandCreateForm.tsx` — catch surfaces real error message instead of fixed string.

### Tests

Server suite green: **157/157**.

## Session ~01:55 — Sessions "Stop" button no-op fix (DB-authoritative stop)

**Commit:** `6608b42` (branch `fix/sessions-stop-db-authoritative`, merged to `develop`)

### Symptom

A viral session spawned via Campaigns "Approve & Run" sat at `waiting`. Clicking **Stop** on the Sessions page did nothing — row stayed `waiting`. A direct `POST /api/sessions/:id/stop` (from an earlier moment) *did* transition it `waiting` → `done`. Same endpoint, different behaviour depending on when it ran.

### Root cause

`POST /api/sessions/:id/stop` (`server/routes/sessions.ts:76`) guarded existence against the **in-memory `SessionService` Map** only (`getSession`). The Map, `GET /api/sessions`, and the `PtyService` are all **process-lifetime** — a server restart, or a `tsx watch` reload on any save in dev, wipes them, but the durable `agent_runs` SQLite row survives (stuck at `waiting`). After a reload the UI Stop hit a **Map miss → 404**, and the client **swallowed** it (`SessionBoard.tsx:25` `catch(() => {})`), refetching only on success — so the stale row never cleared. The direct call that "worked" ran against a process where the id was still live in the Map.

**Server-side bug** (the 404 guard) with a **client-side aggravator** (swallowed error + no fallback refetch).

### Fix

- `server/services/session.service.ts` — `stopSession` is now DB-authoritative and returns `boolean`: best-effort PTY kill regardless of Map state, then finish the live session if present, else fall back to the `agent_runs` row (non-terminal → `done` + emit `status`). Returns `false` only when the id is in neither Map nor DB.
- `server/routes/sessions.ts` — stop route 404s only when `stopSession` returns `false`.
- `client/src/components/SessionBoard.tsx` — `stop` now always refetches (`.finally(refresh)`) and surfaces the error in a banner instead of a silent no-op.

### Tests

- New: `test/sessions.route.test.ts` — "STOP transitions an orphaned waiting run (no live session) to done" (asserts run → `done`, `completedAt` set, PTY kill requested) + "STOP still 404s when the id exists in neither the Map nor agent_runs". Enhanced `FakePtyService` to record kills.
- **Confirmed the orphan test FAILS with 404 when the fix is reverted** (reproduces the bug), passes with the fix.
- Server vitest: **159 passed / 1 skipped** (baseline 157/1 + 2 new).
- Client build (`tsc -b && vite build`): **success**.
