### Endpoint-deviation decisions (vs. original brief)

1. **Approval PATCH shape:** Brief said `POST /api/approvals/:id {status, reviewNotes}`. Real Plan-1 endpoint is `PATCH /api/approvals/:id/status {status, reviewedBy, reviewNotes}`. Client uses the real endpoint.

2. **Task follow-up on approve is client-side:** Server does NOT auto-transition the task when an approval is decided. `useApprovals.decide()` performs the follow-up `PATCH /api/tasks/:taskId/status` itself:
   - `approved` → task `done`
   - `rejected` / `changes-requested` → task `in-progress`

3. **Campaign approve endpoint:** `POST /api/campaigns/:id/approve {approvedBy: "Robin Dutta"}` — not a status PATCH.

4. **`POST /api/sessions/start` is Plan-3 stub:** Called with `{ campaignId }`. Returns 404 today. `CampaignPanel.run()` catches 404/not-found/failed-to-fetch and surfaces "Session engine not yet available (lands in Plan 3)." banner. Campaign is approved and ready when this path is hit.

5. **Brand registration falls back to vault write:** `POST /api/setup` only accepts `{ stepId }` for progress toggles — no brand record support. `registerBrand()` in `intake.api.ts` uses `saveToVault('brands/<id>.md', ...)` instead. Plan 3/4 should be aware: brands live in the vault at `brands/<id>.md`, not in the DB setup table.
